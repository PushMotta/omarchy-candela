Design review 02 · 5 October 2026 · for Candela 1.2

Workspace planner

Give each of Omarchy's ten workspaces a home display. SUPER+6 then opens on the display you chose, and the plan survives reboots and docking. Candela does nothing else with workspaces.

Target Omarchy 4.0.4 · Hyprland 0.56.2 (Lua) Ships in 1.2, with the three fixes from the comparison Hyprland behaviour read in the v0.56.2 source, not yet run on this desk Status awaiting your decisions before code
Scope

What it does

It gives each workspace from 1 to 10 a home display, and gives each display the workspace it shows when it lights up. Both are written as Hyprland workspace rules into candela-layout.lua, the file Candela already owns, and they go through the same apply, keep and revert as everything else.

What it leaves alone

It doesn't touch names, icons, apps per workspace, overviews or the bar's workspace widget. Omarchy's SUPER+L layout toggle keeps working on top of the plan. The marketplace already has dozens of plugins for those things.

Why it belongs in Candela

Where workspaces live depends on the arrangement. It changes when a display is switched off, mirrored or unplugged, so it needs the same transaction. Candela also tells these two MateViews apart, which a rule based on the display description can't do here.

What Hyprland already does

How it is written

Rules in the layout file, and moves Candela makes itself

Intent

The intent file gets a workspaces block with a home for each workspace and the workspace each display shows when it lights up. Without the block, the plan is Off. Presets only fill in the homes, so Off can never switch itself back on, and a display Candela hasn't seen before never gets a plan nobody gave it.

Same rule as Omarchy's

Hyprland merges rules whose workspace text matches exactly into one, field by field (WorkspaceRuleManager.cpp:25-32). Candela writes workspace = "3" in the same form as Omarchy's layout toggle, so layout = "scrolling" and monitor = "DP-2" become one rule and both apply.

Because of that merge, Candela never disables its rule. Switching off the shared rule would switch off Omarchy's layout too. Removing a plan reloads Hyprland, which is how Candela reverts already.

Moves after the reload

A reload doesn't move open workspaces, so Candela does: one hl.dispatch(hl.dsp.workspace.move{…}) for each open workspace that is away from a home that's connected. Moving the workspace you're looking at takes focus and the pointer with it, so that move goes last. Candela then reads back workspacerules -j and workspaces -j, the same way it checks a display change.

-- appended to candela-layout.lua after the monitor rules (Split, this desk)
hl.workspace_rule({ workspace = "1", monitor = "DP-1", default = true })
hl.workspace_rule({ workspace = "2", monitor = "DP-1" })
-- … 3 to 5 on DP-1
hl.workspace_rule({ workspace = "6", monitor = "DP-2", default = true })
-- … 7 to 10 on DP-2
$ omarchy-candela apply '{"workspaces":{"homes":{"6":"DP-2","7":"DP-2"}}}'
$ omarchy-candela apply '{"workspaces":null}'          # Off: rules gone, nothing moved
$ omarchy-candela workspaces home                     # send every open workspace home, bindable
$ omarchy-candela state | jq .workspaces               # plan, and where each open one is now

Revert

The pending record also stores where each open workspace was before the change. Revert reloads, which removes the rules, and then moves each workspace back. The move-back is required, because the reload alone leaves them where the plan put them.

Validation

Homes are workspaces 1 to 10. The display named must be one Candela knows. It can't be a mirror or Hyprland's FALLBACK output. A display can only show a workspace that is homed on it. merge_intent rejects anything else, so the CLI follows the same rules as the Studio.

Displays that aren't connected

Today the generator writes rules only for connected displays (bin/omarchy-candela:351), so keeping a change while DP-2 is unplugged drops DP-2's rules. That is fix 1 for 1.2. The planner depends on it, because DP-2's homes have to stay in the file while DP-2 is gone.

The two MateViewsBoth report Huawei Technologies Co. Inc. MateView. Hyprland matches desc: by prefix and takes the first display that connected, so a description can't tell them apart. The plan names connectors, as the monitor rules already do.

Set to mirrorA mirror shows another display's picture, so it can't be a home. Its homes move to the display it mirrors as part of the same change, and the summary says so.
Laptop lidOmarchy's clamshell script switches the panel off, which takes the unplug path. The laptop's workspaces park on the external display and come back when the lid opens. Not testable here: no laptop.
Virtual displays (1.3)Creating one counts as a display connecting, so it pulls every planned workspace home. A virtual display can also become the parking place when another display unplugs, which would hide workspaces on a screen nobody can see. 1.3 has to handle both.
Your own workspace rulesYou have none today. A rule with the same workspace text merges, and Candela's value wins because its file loads later. doctor reports a workspace whose live rule names a different display from the plan.

The barOmarchy's workspace widget is the same on every bar: it shows 1–5 plus any open 6–10 and highlights only the focused workspace. The plan doesn't change that, and changing it is a bar plugin's job. state exposes the plan so such a plugin could read it.

Decisions needed

Eight calls before code

  1. Off until you turn it on. No rules are written and nothing moves until a plan is chosen, and a new display never gets one automatically. Recommend: yes.
  2. What gets stored. Either the plan itself (a home per workspace), with presets that only fill it in, or a preset name that Candela expands each time. Recommend: store the plan. A stored preset name has to guess what to do when a display appears, and that guessing is where these features misbehave.
  3. How a display is named. By connector (DP-1), as the monitor rules already are, or by desc: when the description is unique. Recommend: connector now. On this desk a description can't work, so it's best introduced with saved profiles.
  4. Persistent workspaces. None, the first per display, or all planned ones. Recommend: none. Use default for the first per display instead. With a home set, SUPER+N already opens in the right place. Persistent empty workspaces would add stops to SUPER+TAB, and the bar can't tell them apart from closed ones.
  5. No countdown for a workspace-only change. It applies and is kept at once, and Revert puts back the previous plan and placement. A change that also touches a display keeps the 15 s countdown for everything. Recommend: yes. The countdown exists for changes that can blank a screen, and a plan can't.
  6. Apply moves open workspaces home. The summary names every move first. The alternative leaves open workspaces where they are until the next display connects. Recommend: move them. Otherwise the canvas shows a plan the desk doesn't match.
  7. Where it lives. An inspector section after Colour, plus chips on the canvas, with the popup unchanged. Or a separate Workspaces mode in the Studio. Recommend: section and chips. It keeps the keyboard row model and adds no new mode to learn.
  8. What 1.2 contains. The planner, plus the three fixes: rules kept for unplugged displays, the FALLBACK check, and the text size slider. Recommend: yes, released after 1.1.0.

Once these are decided, the approved version goes into DESIGN.md (§3.2 inspector, §6 architecture, §7 scope), and design review 01 stays as it is.
